# Stage 5: Staged execution (M5)

**Input:** a confirmed plan (`POST /projects/{id}/plan/confirm`) freezes the scenario ids, repeats, levers and hard cap. `POST /projects/{id}/runs` creates a run from it (cap can be overridden).
**Stages** (`pipeline/runner.py`):
1. **Smoke** (10% of the cases, at least 3, 2 repeats): fails the run early if a prompt placeholder has no value in a scenario or a judge's output cannot be parsed; runs an A/A control (old r0 vs old r1) for pairwise metrics; measures old-vs-old noise; warns if the noise is too high to call individual cases (with the repeats needed).
2. **Main** (the tier): per case, repeats of old and new, programmatic checks first, then judges. Adaptive repeats / early stopping use ONE rule: a case where every metric is *unchanged* and both arms are identical and constant stops after 2 repeats. Anything else (a flag, a suggestive difference, an unstable arm, arms that differ) runs to the maximum (`max_repeats_adaptive`): **a flag is never stopped early, it is confirmed.** Stopping on a flag at 2-3 repeats inflated false alarms in measurement.
3. **Deep dive**: generates neighbours of broken cases (`deep_dive_per_regression`, capped at `deep_dive_max_scenarios`) and runs them. If that would exceed the cap the run **pauses and asks** (`deep_dive_needs_budget`).
**Stop rule (measured):** after 2 repeats a case stops when every metric that repeats CAN still decide is either decided (flagged by the exact, corrected test) or unchanged with identical arms. A metric that cannot reach significance within the repeat budget (typically the noisy pairwise judge) is ignored by this rule, otherwise every case ran to the maximum repeats. `PV_CONFIRM_FLAGGED=true` additionally keeps running flagged cases to the maximum: measured on independent no-op draws it changed nothing (0 of 28 runs flagged either way) while costing 24% more and finding fewer real regressions, so it is off.
**Hard cap:** `LLMClient` raises before a paid call at the cap; the run pauses (`cap`) and waits for `extend` (raise the cap and continue) or `stop` (partial report). In-flight calls finish, so spend can exceed the cap by at most a few calls. Cache hits are free and never blocked.
**Resume / crash safety:** every row is looked up before a call and calls are cached, so resuming is re-running the same code: no duplicate paid calls (tested: unique cache keys and result rows after cap pauses, provider crashes and a simulated restart). A provider error pauses the run (`error: ...`) keeping all state. On startup, runs left `running` become `paused (interrupted)`; they never resume themselves (nothing is spent unasked). `POST /runs/{id}/resume | extend | stop`.
**Live:** `GET /runs/{id}/events` (SSE): snapshot, stage, noise, progress (spend vs cap), regression (surfaced as each case completes), warning, cap/deep-dive pause, done. In-memory bus, history replayed for late subscribers, reset on (re)start.
**Judges:** `programmatic_first` skips a pointwise judge on an output that already failed a programmatic check; the pair is then dropped from that metric (strict pairing) rather than counted, and the report says how many calls were skipped.

**Stale tracking (`pipeline/stale.py`):** changing upstream data marks the downstream stages that were already DONE (prompts -> everything; analysis -> scenarios onward; scenarios -> metrics onward; metrics -> budget onward; a new plan -> run and report). Approving a scenario or metric is not a change. Redoing a stage (regenerating scenarios, designing metrics, estimating, running) clears its own mark; `GET /projects/{id}/stale` and `POST /projects/{id}/stale/{stage}/ack` ("it is still right"). The UI marks the stepper and shows a banner. Nothing is recomputed automatically. **Restart recovery** now also fails orphaned job and optimization rows with a clear message (their tasks died with the process; cached calls replay for free).
