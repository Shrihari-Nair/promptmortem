# Stage 3: Metrics (M3)

**Agents:** `metric_designer` (temp 0.3), `judge` and `pairwise_judge` (temp 0). Prompts in `backend/app/agents/prompts/`. The designer prefers programmatic checks, must give every pointwise judge metric pass and fail examples (the Pydantic validator rejects specs without them, which triggers a repair-retry), and keeps the set small (cap 12). The code always adds one pairwise **regression** metric and, when the dataset has gold `expected` values, an `equals $expected` metric (verified tier).
**Programmatic engine (`pipeline/metrics_engine.py`):** declarative only, no code execution. Check types: max_words, min_words, max_chars, regex_required, forbidden_regex, contains_all, contains_none, json_valid, json_schema, equals (`"$expected"` = the scenario's expected output), starts_with, language_is. Aggregates: all_pass, any_pass, mean. Specs are validated on create/edit (422 on bad regex, bad JSON schema, missing fields).
**Judges are blind:** prompts say "output A / output B" and never old/new. The pairwise judge runs both orders; if the two disagree the case is `disputed` and the verdict is `tie`. Judge calls are cached, so re-scoring identical outputs costs nothing.
**Human actions:** approve / reject (with comment, fed to the next design round) / edit definition, applies-to, weight; add own metric; **preview** on 3-5 sample outputs (generated from the new prompt, or from samples you paste; pairwise previews also generate the old output).
**Calibration (`POST /metrics/{id}/calibrate`):** agreement between a pointwise judge and YOUR labels. Only explicit labels count: a trace or dataset row with an observed `output` and `expected` = pass | fail. Free-text `expected` values are NOT assumed to be gold replies (they are usually descriptions of the wanted behaviour, which no judge could pass as a reply; found on real data) and are used as the scenario's expected behaviour. Agreement is stored overall and per label (a lenient judge shows up as low agreement on the `fail` label). The labels should be about what the rubric checks: a tone judge calibrated on labels about refund policy will agree poorly, correctly. **The regression judge** is built with the app's constraints and the INTENDED changes from the diff analysis and told not to reward length or polish: on real Gemini an unprimed pairwise judge rated 18 compliant concise replies as regressions (verbosity bias), which would have turned a successful prompt change into a BLOCK.
**Regenerating** replaces untouched proposals; approved, edited and rejected metrics are kept.

**Second judge (optional):** a pointwise rubric can opt in (`ensemble: true`, `ensemble_model` or `PV_JUDGE_ENSEMBLE_MODEL`): a second, different judge also scores each output. The primary verdict stands; a disagreement is stored (`Score.disputed` plus the second judge's reasoning) and shown in the report as the second-judge disagreement rate. Without a second model configured the flag is ignored. Verdict overrides are fed to the metric designer too ("the metrics may be too strict or too lenient").
