# Stage 8: Prompt refinement with GEPA (M8)

`POST /projects/{id}/optimize {cap, max_metric_calls?, n_candidates?}` (job). **A hard cap is required**; it covers the search AND the held-out validation.
**What is optimized:** the *new* prompt. DSPy's `GEPA` is used with: a one-predictor program whose instruction IS the prompt template; a custom adapter (`optimize/dspy_bridge.py`) that renders it with `{{var}}` exactly like the runner (so GEPA scores what we would send); a custom LM that routes every DSPy call through `LLMClient` (cache, cost, hard cap); our metrics as the metric function (programmatic first, judges only if those pass; the score AND a textual explanation of why it was low go back to the reflector); and our `reflector` agent (`agents/prompts/reflector.v1.md`) as the proposal step: minimal edits, constraints and placeholders kept, no copying of example inputs (a retry, then an error). A candidate that drops a `{{placeholder}}` gets it appended back.
**Data split:** approved scenarios if there are at least `gepa_reviewed_min` (30) of them; otherwise all non-rejected scenarios, with a warning (restricting to a handful of approved rows gave a 5/3/4 split on real data, too small to validate anything), 30% held out stratified by cluster (`heldout_fraction`), the rest split into GEPA train/validation (70/30). **Held-out scenarios are never shown to the optimizer:** tested by spying on every target, judge and reflector call during the search. Regressions from the last report are given to the reflector only for train/val cases.
**Validation:** each candidate is saved as prompt version `candidate_N` and compared with the new prompt AND with the old prompt on the held-out scenarios by the ordinary stage-6 paired, noise-adjusted analysis (a normal run with `compare` labels, no deep dive). Each result is a full report (`/runs/{id}/report`).
**Human loop:** accept (optionally promote to `new`; the previous `new` is kept as `new_prev_N`), edit (saved as a NEW candidate, validated like the others; placeholders must be kept), reject with a comment. Every action is stored as feedback and fed to the reflector in the next optimization (with the rejected candidate's opening text).
**Cap:** GEPA ends at the cap via its stop callback; the optimization is `paused` and no held-out validation runs. GEPA is not resumable, but the cache is keyed by content and the search is seeded, so a retry replays the paid part for free. If the cap is hit during validation, `POST /optimizations/{id}/candidates/{cid}/evaluate {cap}` resumes the paused comparisons.
**Known debt:** `LLMClientLM` subclasses DSPy's `BaseLM.forward`, deprecated in DSPy 3.4 and removed in 3.5 (pinned `<3.5`); migrate to the engine interface then.
